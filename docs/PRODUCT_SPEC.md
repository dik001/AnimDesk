# AnimDesk 1.0 — спецификация продукта

## Назначение

AnimDesk — персональная библиотека аниме для Windows 10/11. Приложение помогает найти аниме, сохранить его локально, назначить статус и вручную отмечать просмотренные серии. Регистрация и серверный профиль не нужны.

## Объём версии 1.0

### Пользовательские сценарии

1. Найти аниме через реальный внешний источник метаданных.
2. Открыть страницу конкретного сезона и увидеть его метаданные.
3. Добавить сезон в локальную библиотеку с одним из пяти статусов:
   - `watching` — смотрю;
   - `planned` — в планах;
   - `completed` — просмотрено;
   - `on_hold` — отложено;
   - `dropped` — брошено.
4. Вручную изменить число просмотренных серий.
   При выборе статуса «Просмотрено» все серии отмечаются просмотренными, если их общее число известно и положительно. При неизвестном числе серий прогресс сохраняется; прочие статусы его не сбрасывают.
5. Просмотреть библиотеку, локальный профиль и статистику.
6. Настроить приложение, экспортировать или импортировать локальные данные.
7. Открыть ранее сохранённые данные без сети.
8. Поставить или снять личную оценку 1–10; она хранится локально отдельно от рейтинга каталога.

### Не входит в версию 1.0

- просмотр видео и встроенный видеоплеер;
- выбор или каталог озвучек;
- рецензии пользователя;
- скачивание серий;
- авторизация, регистрация и синхронизация с серверным аккаунтом.

### Личные оценки

Личные оценки 1–10 добавлены по прямому запросу пользователя: отдельная локальная таблица `anime_ratings` с ключом профиль + внутренний anime.id. Оценки можно ставить независимо от добавления в список; они не отправляются внешним API и не заменяют рейтинг каталога.

## Данные

- Единственный источник пользовательских данных — локальная SQLite-база.
- Единственный онлайн-источник метаданных — Shikimori GraphQL, endpoint `https://shikimori.io/api/graphql`. Ошибки получения метаданных отображаются явно, а не заменяются фиктивным успешным результатом.
- Внешние API предоставляют только метаданные и не получают пользовательские статусы, прогресс или заметки.
- Каждая локальная запись имеет внутренний SQLite ID, исходную пару `provider + providerId`, nullable `shikimoriId` и nullable `malId`.
- Известные `shikimoriId` и `malId` уникальны. `NULL` означает, что соответствие неизвестно, и может встречаться у нескольких записей.
- Сопоставление выполняется только по точной паре `provider + providerId` или достоверному внешнему ID. Противоречащие друг другу идентификаторы считаются конфликтом; записи не объединяются автоматически.
- Каждый сезон — самостоятельная запись. Похожие названия не являются основанием для объединения.
- Сохранённые метаданные доступны офлайн. Сетевые ошибки отображаются явно и не превращаются в «пустой успешный результат».
- Экспорт и импорт должны иметь версионируемый формат и проверку входных данных.

## Архитектура

Технологический стек: Tauri 2, Rust, React, TypeScript, Vite, Tailwind CSS, React Router, lucide-react, npm.

Клиент разделён на небольшие слои:

- `src/app` — запуск приложения, маршрутизация, общие провайдеры и каркас окна;
- `src/pages` — страницы маршрутов без бизнес-хранилища;
- `src/components` — переиспользуемые визуальные компоненты;
- `src/features` — законченные пользовательские функции;
- `src/services` — внешние API и инфраструктурные сервисы;
- `src/repositories` — контракты и реализации доступа к локальным данным;
- `src/types` — общие доменные типы.

Пользовательские данные хранятся через официальный Tauri 2 SQL plugin. Сетевые запросы выполняет Rust; фиктивные ответы и демонстрационная статистика допустимы только в тестах. Реализованы поиск, карточки, локальная библиотека, ручной прогресс, заметки, оценки, профиль, статистика, темы, кеш обложек, аватар и экспорт/импорт. Статистика вычисляется из сохранённых записей. При отсутствии сети доступны уже сохранённые данные. Контракты каталога описаны в `docs/CATALOG.md`.

## UX и визуальный язык

- тёмный графитовый фон по умолчанию, сохраняемая светлая тема и умеренные фиолетовые акценты;
- нативная рамка и заголовок окна Windows;
- постоянная боковая навигация, компактная на узком окне;
- карточки аниме с обложкой, когда реальные данные доступны;
- чёткие loading, error и empty states;
- кнопки незавершённых функций отключены и явно подписаны;
- видимый клавиатурный focus, корректные landmarks и reduced motion.

Минимальный размер окна: около 1000 × 650 px.

Навигация реализована через `createHashRouter`: логические маршруты сохраняются, а адреса имеют вид `/#/library`. Это позволяет открывать и перезагружать страницы в локальной сборке Tauri без HTTP-сервера. Экраны загружаются отдельными чанками, каркас навигации остаётся на месте во время загрузки.

## Безопасность

- Content Security Policy остаётся включённой.
- Tauri capabilities минимальны и не дают доступ к shell или произвольным командам.
- HTML не вставляется небезопасным способом.
- Секреты не хранятся во фронтенде; если выбранный публичный API не требует ключа, ключи не вводятся вовсе.

SQL-слой использует точечные разрешения `sql:default` и `sql:allow-execute`; shell и широкие файловые разрешения не выдаются. CSP разрешает обложки только с точных доверенных HTTPS-хостов Shikimori и `cdn.myanimelist.net`; внешние соединения браузеру не разрешены. Метаданные запрашиваются узкой Rust-командой у точного хоста `shikimori.io`, без редиректов и произвольных URL. Запросы других каталогов отклоняются до сетевой операции. Основания: [capabilities Tauri](https://v2.tauri.app/security/capabilities/) и [CSP Tauri](https://v2.tauri.app/security/csp/).


## Разработка и проверка

Поддерживается только Windows 10/11; мобильные платформы, Electron и Next.js не входят в архитектуру. TypeScript работает в строгом режиме. Модули разделяются по ответственности. Интерфейс русскоязычный, с семантической разметкой, подписями контролов, достаточным контрастом, клавиатурной навигацией и поддержкой `prefers-reduced-motion`. Заголовок окна нативный.

Новые разрешения Tauri вводятся только для конкретной функции и с минимальной областью доступа. Произвольные команды, отключение CSP и небезопасная HTML-вставка недопустимы. После значимых изменений выполняются доступные lint, typecheck, test, build и Rust check; фактические результаты и ограничения записываются в `docs/PROGRESS.md`. Следующий этап начинается по отдельному запросу.
